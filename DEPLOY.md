# Deploying the portal

The portal has four parts. All of them can run on free plans, and all of them
can move to any other host later: the servers are ordinary Docker images.

| Part | What it is | Free host (recommended) | Runs anywhere as |
|---|---|---|---|
| **Website** | Static files (React, plus the engine in WebAssembly) | GitHub Pages: live now at https://aravindjk03.github.io/invty-ghg-portal/ | any static host: Cloudflare Pages, Netlify, Vercel, S3 |
| **Backend API** | Accounts, sign-in, leads, audit, admin console data | Render free web service | `backend/Dockerfile` |
| **Database** | Postgres | Neon free (data kept; sleeps when idle, wakes in about a second) | any Postgres 14+ |
| **AI estimate service** | INSITY EDGE AI for Product Carbon | Render free web service | `Dockerfile.ai` |
| **Admin site** | The operations console, a separate website | Cloudflare Pages, behind Cloudflare Access | any static host, **never GitHub Pages** |

For the ordered first-time setup, follow **[docs/GO-LIVE-CHECKLIST.md](docs/GO-LIVE-CHECKLIST.md)**.
This page explains each part.

---

## Database: Postgres (Neon, free)

The backend stores accounts, sessions, leads, audit chains and the console
logs. Where it keeps them depends on `DATABASE_URL`:

- **Set:** Postgres. Use this on every host. Free plans on Render, Koyeb and
  Cloud Run wipe the server's disk on each deploy or restart, so the next
  option would lose every account.
- **Not set:** a SQLite file in `backend/data`. This is fine on your own
  computer, and it's what the tests use.

Neon setup: the repository is already linked to the Neon project
`hidden-fire-39540730`, branch `production`, in AWS Singapore (`neon.ts`, `.neon`).
1. `npm i -g neon@latest`, then `neon login`.
2. `neon deploy` (or `neon env pull`) writes the branch's settings to
   `.env.local` at the repo root, which is git-ignored:
   - `DATABASE_URL`: pooled (`-pooler`) connection string
   - `DATABASE_URL_UNPOOLED`: direct connection string
   - `NEON_BRANCH`, `NEON_BRANCH_ID`

   The backend reads that file for local runs, so `npm run dev:backend` uses
   Neon with no copying.
3. On the host (Render), set `DATABASE_URL` to the **pooled** string and
   `DATABASE_URL_UNPOOLED` to the **direct** one. The tables are created over
   the direct connection on first start; there is no migration command to run.

Driver: the backend uses `node-postgres` (`pg`) over TCP with the pooled string,
as Neon recommends for a long-running server. On serverless or edge hosts, or
any network that only allows HTTPS, set `DATABASE_DRIVER=neon-http` to use
Neon's serverless driver over HTTPS instead. Note that this driver queues
console-log writes within one server process only, so run a single instance
with it.

Any other Postgres works the same way: Supabase, Aiven, RDS, Cloud SQL, or the
`db` service in `docker-compose.yml`.

## Backend API on Render (free)

`render.yaml` describes it. On render.com: **New**, then **Blueprint**, pick
this repository. Render asks for each value marked `sync: false`:

| Variable | Value |
|---|---|
| `DATABASE_URL` | The Neon connection string. |
| `ADMIN_EMAIL` | Your email. On the first start the backend creates this administrator and prints a **one-time password** in the Render log (**Logs** tab). Sign in with it and change it. |
| `GOOGLE_CLIENT_ID` | Your Google client ID ([SETUP-GOOGLE.md](SETUP-GOOGLE.md)). Leave empty until you have one. |
| `ADMIN_ORIGIN` | The admin site's address, once it exists. Empty until then. |

`JWT_SECRET`, `API_SECRET_KEY` and `ESTIMATE_SERVICE_SECRET` are generated by
Render; there is nothing to paste. `CORS_ORIGIN` is already set to the GitHub
Pages address.

Check it works: open `https://iinvty-backend.onrender.com/api/health`. It
should say `"status":"healthy"` and `"database":{"kind":"postgres","reachable":true}`.

A free service sleeps after 15 minutes idle and takes about 30–60 seconds to
wake on the next request. The data is safe in Neon either way.

**Alternatives** that take the same Docker image and the same variables:
- **Koyeb:** free, one service. New service, Docker, `backend/Dockerfile`.
- **Google Cloud Run:** free tier, scales to zero.
- **Fly.io** or **Railway:** paid with small trials.
- **Any VPS with Docker:** see below.

## AI estimate service on Render (free)

Also in `render.yaml`. It asks for `GEMINI_API_KEY`: a free key from
**aistudio.google.com**, created in a project with **no billing** so it stays
free. `ESTIMATE_SERVICE_SECRET` is shared with the backend automatically.
`BACKEND_BASE_URL` must be the backend's address with `/api/v1`; change it in
`render.yaml` if Render gives the backend another name.

Health: `https://iinvty-insity-edge-ai.onrender.com/health` reports
`"ai_ready": true` once a key is set.

## Website (GitHub Pages)

Built on your machine and pushed to the `gh-pages` branch. The server addresses
are baked in **at build time**, so publish again whenever they change:

```bash
npm --prefix frontend install          # first time, or after dependency changes
IINVTY_BACKEND_URL=https://iinvty-backend.onrender.com/api/v1 \
IINVTY_AI_URL=https://iinvty-insity-edge-ai.onrender.com \
IINVTY_GOOGLE_CLIENT_ID=<your client id> \
npm run deploy:pages
```

| Variable | Sets | Without it |
|---|---|---|
| `IINVTY_BACKEND_URL` | Accounts, sign-in, leads | **The script refuses to publish**, unless you pass `-- --trial` to publish the browser-only trial on purpose (accounts kept in each visitor's browser). |
| `IINVTY_AI_URL` | Product Carbon estimates | Estimates are unavailable. |
| `IINVTY_GOOGLE_CLIENT_ID` | Google sign-in | The Google button is hidden. |

There is **no AI key variable**, on purpose. Anything built into the site can
be read by every visitor, so the AI key lives only on the estimate service.

Needs Node 20 or newer, and push access to the repository. The script builds
with base path `/invty-ghg-portal/`, adds one commit on `gh-pages`, and pushes.
It never rewrites history.

**Other static hosts:** run `npm --prefix frontend run build` with the same
`VITE_API_BASE_URL`, `VITE_PCF_API_BASE_URL` and `VITE_GOOGLE_CLIENT_ID`
(and `VITE_BASE_PATH=/`). Then upload `frontend/dist` to Cloudflare Pages,
Netlify or Vercel. Add the new address to `CORS_ORIGIN` on the backend, to
`PCF_CORS_ORIGINS` on the AI service, and to the Google client's Authorised
JavaScript origins.

## Admin site (operations console)

A separate website, so the customer site holds none of its code.

```bash
cd frontend
VITE_API_BASE_URL=https://iinvty-backend.onrender.com/api/v1 npm run build:admin   # -> frontend/dist-admin
```

1. On **Cloudflare Pages** (free): **Create**, then **Pages**, then **Upload
   assets**, then upload `dist-admin`. You get `https://<name>.pages.dev`.
   Pick an unguessable name.
2. Protect it with **Cloudflare Zero Trust**, then **Access**, then
   **Applications**, then **Add**, then **Self-hosted**, for that address. Add
   a policy allowing only your team's emails. It's free for up to 50 users.
   Visitors then can't even load the page.
3. On the backend, set `ADMIN_ORIGIN=https://<name>.pages.dev`. The console API
   then answers only that site; from anywhere else it looks like a route that
   doesn't exist. Optionally also set `OPS_ALLOWED_IPS` to your office or VPN
   range.

Never put it on GitHub Pages: that is public and tied to this repository.
Details: [docs/OPS_CONSOLE.md](docs/OPS_CONSOLE.md).

## Anywhere with Docker (a VPS, or your own server)

```bash
cp backend/.env.example backend/.env    # set JWT_SECRET, API_SECRET_KEY, ADMIN_EMAIL, CORS_ORIGIN …
cp service/.env.example service/.env    # set GEMINI_API_KEY, PCF_CORS_ORIGINS
POSTGRES_PASSWORD=<a strong password> docker compose up -d --build
curl http://localhost:5000/api/health
```

This runs Postgres (with a persistent volume), the backend on port 5000 and the
AI service on port 8000. Put a reverse proxy with HTTPS in front, for example
Caddy (`reverse_proxy localhost:5000`) or Nginx. Free always-on servers:
**Oracle Cloud Always Free** and **Google Cloud e2-micro**.

## Rolling back the website

`gh-pages` keeps every publish. The safe way is to check out the source commit
that a publish names, then run `npm run deploy:pages` again. To point
`gh-pages` straight back at an older publish:

```bash
git fetch origin gh-pages
git log --oneline origin/gh-pages
git push origin <that-commit>:gh-pages --force-with-lease
```

## Your own domain (later)

1. DNS: `CNAME app` → `aravindjk03.github.io` (or your static host).
2. Put a file `frontend/public/CNAME` containing `app.yourdomain.com`, so the
   setting survives each deploy.
3. GitHub, then **Settings**, then **Pages**: set the custom domain and tick
   **Enforce HTTPS**.
4. Add the new address to:
   - `CORS_ORIGIN` on the backend
   - `PCF_CORS_ORIGINS` on the AI service
   - the Google client's Authorised JavaScript origins
